Implemented VM-scoped repository credentials under `aivm vm creds`, using one dedicated GitHub deploy key for each VM/repository pair. The host creates and retains the keypair, registers only the public key through `gh`, installs the private key into the selected guest, and writes exact Git URL rewrites so normal clone/pull/push commands select the correct per-repository identity. The config store now records non-secret credential metadata under the owning VM, and revocation invalidates the provider key before attempting guest or host cleanup.

I deliberately kept branch policy out of AIVM and made read-only the default with an explicit `--write` opt-in. I also chose to block VM deletion while an active credential exists rather than silently revoking or orphaning access during an unrelated lifecycle command. A provider-revoked credential may remain in `revocation-pending` when the VM is unreachable; deletion is then safe and removes the remaining host state. The main remaining risk is integration behavior against a real GitHub repository and real `kwconf` dispatch, because this environment's package mirror repeatedly returned HTTP 503 and direct PyPI DNS was unavailable. The resolver, store schema, generated guest configuration, mocked provider lifecycle, failure recovery, deletion guard, and direct dry-run command were exercised locally; I am confident in the state transitions and conservative revocation ordering, but a live deploy-key smoke test should still be done before release.

Performed an adversarial review of the initial VM deploy-key implementation after its tests passed in the user's environment. The happy-path lifecycle was coherent, but the review exposed security-sensitive assumptions that the original tests did not challenge. In particular, remote-key selection preferred the mutable host public-key file over the credential identity recorded in the config store. A changed host key could therefore redirect revocation toward a different deploy key. I changed provider identity resolution to use the stored provider id and SHA256 fingerprint, reject mismatches, and verify that GitHub no longer reports the key before local cleanup.

I also made credential parsing fail closed. Previously, a malformed nested credential table could be silently discarded, which weakened the VM-deletion guard and could orphan a live provider authorization. Required fields, supported states/access modes, duplicate ids, and duplicate repository scopes are now validated by both the parser and config lint. Guest SSH configuration now uses batch mode and first-use host-key acceptance so a fresh VM does not hang or fail on the first Git operation. Git URL rewrites were narrowed to canonical `.git` URLs because Git's `insteadOf` matching is prefix-based and the broader rewrite could capture similarly named sibling repositories.

The expanded tests cover split-store round trips, malformed and duplicate records, repository-input injection syntax, host-key fingerprint drift, remote-id/fingerprint disagreement, failed provider deletion verification, read-only provisioning, first-use SSH settings, and Git rewrite prefix collisions. Forty-two targeted tests pass in the local dependency-stub environment; one real `kwconf` dispatch test remains deselected because the package mirror is unavailable here. I am confident the highest-risk local state and revocation failures are now covered. The remaining release risk is a live GitHub/VM end-to-end smoke test, particularly actual deploy-key creation, first SSH connection, pull, push for write grants, and provider revocation.
