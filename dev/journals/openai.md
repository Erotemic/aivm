## 2026-07-15 16:58:00 -0400
Fixed the base-image bootstrap failure seen on a fresh remote host. The configured artifact checksum was sound, but the URL pointed at Ubuntu's dated daily-build tree, whose older directories are eventually removed. I changed the default to Ubuntu's retained `release-20260225` archive, which contains the same amd64 image under the release filename and the same pinned SHA256, and added a compatibility rewrite so configs generated with the former built-in URL recover automatically.

The second issue was command-plan sequencing rather than curl itself: the transfer used `check=False`, so the grouped plan continued to `mv` and `sha256sum` before Python inspected the transfer result. I made the transfer a checked command. A failed curl/copy now aborts the plan immediately, before the staging path can be promoted or hashed, and the caller receives a domain-level error explaining that the cache was not installed. I deliberately did not add a moving `current/` URL or online checksum discovery; reproducibility and a small trust surface are more important than silently following the newest image.

The remaining tradeoff is that an interrupted transfer may leave a `.part` file until the next retry. That is safe because it is never promoted, and the first command of every retry removes it. I am confident the original 404 is repaired for both new and existing configs and that future transfer failures cannot be masked by a secondary `mv: cannot stat` error.

## 2026-07-24 14:01:42 -0400
Implemented VM-scoped repository credentials under `aivm vm creds`, using one dedicated GitHub deploy key for each VM/repository pair. The host creates and retains the keypair, registers only the public key through `gh`, installs the private key into the selected guest, and writes exact Git URL rewrites so normal clone/pull/push commands select the correct per-repository identity. The config store now records non-secret credential metadata under the owning VM, and revocation invalidates the provider key before attempting guest or host cleanup.

I deliberately kept branch policy out of AIVM and made read-only the default with an explicit `--write` opt-in. I also chose to block VM deletion while an active credential exists rather than silently revoking or orphaning access during an unrelated lifecycle command. A provider-revoked credential may remain in `revocation-pending` when the VM is unreachable; deletion is then safe and removes the remaining host state. The main remaining risk is integration behavior against a real GitHub repository and real `kwconf` dispatch, because this environment's package mirror repeatedly returned HTTP 503 and direct PyPI DNS was unavailable. The resolver, store schema, generated guest configuration, mocked provider lifecycle, failure recovery, deletion guard, and direct dry-run command were exercised locally; I am confident in the state transitions and conservative revocation ordering, but a live deploy-key smoke test should still be done before release.
