1. Core objective

Determine whether `aivm`’s filesystem attachment design is causing intermittent guest-side `OSError: [Errno 24] Too many open files`, then evolve the design to reduce or eliminate the failure mode.

Subgoals:

* get a reliable MWE / stress harness
* distinguish host-side bind-churn effects from guest-side virtiofs effects
* review and improve the new attachment architecture
* migrate from legacy `shared-root` toward a safer persistent mode
* preserve `ro` guest mounts and backwards compatibility while validating behavior

2. Key context

* The original issue is: inside the VM, normal filesystem operations can start failing with `EMFILE`; even simple `ls` can fail, and restarting the VM clears it.
* The investigation started around attachment handling in `Erotemic/aivm`, especially the old `shared-root` design and PR #15.
* Experiments / MWE work showed:

  * repeated interactive host-side bind churn under a live shared-root export is fragile
  * host teardown often fails with “target is busy”
  * stable host-side staged binds plus guest-side replay/reconciliation is more viable
* That led to the design shift:

  * keep one virtiofs shared export
  * keep host-side staged binds mostly stable
  * persist desired attachments
  * replay guest-visible mounts at boot / reconcile time
  * make `aivm code .` / `aivm ssh .` validate/repair instead of reconstructing everything

Current implementation context:

* New mode introduced alongside legacy mode:

  * old: `shared-root`
  * new: renamed from `declared` to `persistent`
* Persistent mode uses:

  * host staging under `<base>/<vm>/persistent-root`
  * one virtiofs tag `aivm-persistent-root`
  * guest mount `/mnt/aivm-persistent`
  * tokenized subpaths under that mount
  * persisted host manifest + guest replay helper / systemd unit  
* Persistent mode still fundamentally exports a tree containing host-side bind mountpoints, so it remains architecturally similar to the old shared-root topology.

PR review history:

* Initial PR review found:

  * stopped-VM attach did not guarantee boot replay helper availability
  * stale guest state could persist if host manifest disappeared
* Later commits fixed:

  * missing-manifest behavior now fails closed
  * stopped-VM attach refreshes boot-time setup so helper can be present on next boot
  * user-facing mode renamed to `persistent`
* Additional bugs found and diagnosed:

  * helper install script had an indented shebang bug; installed helper path existed but executed as “command not found”
  * stopped-VM cloud-init refresh wrote a token into a root-owned path without sudo, causing `PermissionError`
  * refreshing cloud-init for stopped-VM attach looked too heavy and may cause odd boot behavior
  * SSH host-key mismatch during `wait_for_ssh()` caused apparent hangs; this was later fixed in PR head by fast-failing on common mismatch diagnostics 

Current strongest reproduction evidence:

* Guest `ls /mnt/aivm-persistent` once failed with `Too many open files`
* Guest soft limit was high (`ulimit -n = 1048576`) and system-wide file table low (`file-nr = 2304`), so this is not a simple guest RLIMIT exhaustion 
* `mount | grep aivm-persistent` showed:

  * root mount `/mnt/aivm-persistent` as virtiofs
  * token subpaths also appearing as distinct virtiofs mount entries
* `lsof +D /mnt/aivm-persistent` failed almost entirely in the `geowatch` token subtree with repeated `Too many open files` on `lstat` 
* `rg --files` on `/mnt/aivm-persistent/hostcode-geowatch-5f1a05ef` reproduced the issue
* `strace` showed `EMFILE` returned from both `openat(... O_DIRECTORY)` and `statx(...)` on paths in that `geowatch` token subtree 
* Host-side `virtiofsd` FD-count loop did not show obvious runaway growth during reproduction
* User later clarified there is no `/home/joncrall/code/geowatch` guest bind currently; `geowatch` is not in current attachment config, so the failure is happening on the token subtree inside `/mnt/aivm-persistent`, not on an active guest-visible bind destination.

3. Constraints and preferences

* Keep old `shared-root` working for now; new mode is additive and migration-friendly.
* Preserve read-only guest mount capability.
* Prefer explicit, conservative fixes over magic automation.

  * Example: for SSH host-key mismatch, surface a clear remediation instead of silently rewriting `known_hosts`.
* Prefer systemd-based replay over `/etc/fstab`.
* Avoid aggressive live teardown of host-side bind mounts.
* User wants practical scripts/prompts/reviews, not vague architecture advice.
* Migration should be safe and incremental.
* Future default behavior should eventually prefer `persistent`, but existing attachments should not be silently rewritten.

4. Decisions made

Architecture / design:

* Adopt a new persistent attachment mode instead of replacing shared-root immediately.
* Persist attachment intent and replay guest mounts on boot/reconcile.
* Keep host-side staged binds mostly stable.
* Make `aivm code .` / `aivm ssh .` lightweight reconcile/repair paths.

Naming:

* `declared` was renamed to `persistent`.

Code review decisions:

* Earlier PR versions were not ready due to replay/helper/state issues.
* After later fixes, the stopped-VM replay path was considered substantially improved.
* The latest SSH-host-key mismatch fix looked good and was approved in review, with only a minor non-blocking nit about broad pattern matching in `_is_ssh_host_key_mismatch()` 

Operational decisions:

* For migration from old `shared-root` to `persistent`, safest path is with the VM off.
* Future persistent add/remove operations can happen with the VM on, but the stopped-VM cloud-init refresh path is still viewed as rough.
* Cleanup of stale guest paths should be conservative:

  * only remove empty dirs
  * skip symlinks unless explicitly requested
  * skip mountpoints
  * skip active managed paths

Default attach mode:

* The actual default mode resolution lives in `aivm/attachments/resolve.py` in `_normalize_attachment_mode()`
* CLI help also needs updating separately if the default changes.

5. Lessons learned

Durable technical lessons:

* The core fragility is not just “shared-root” by name; it is the topology of a single virtiofs export containing many host-side bind mount boundaries.
* Persistent mode improves lifecycle / replay / state management, but does not automatically remove the underlying virtiofs+bind-mount risk.
* Guest-side `EMFILE` here is not explained by ordinary shell or system file descriptor limits.
* `statx()` returning `EMFILE` is especially important: this suggests the error is surfacing from lower in the VFS / virtiofs path, not merely from userland forgetting to close FDs. 
* The `virtio_fs_setup_dax: No cache capability` messages are probably incidental, not the main cause.

Durable debugging lessons:

* `lsof +D` on the problematic tree is invasive and can worsen or muddy the situation.
* Better next captures are targeted and comparative:

  * token subtree vs active bind path
  * guest strace on `rg --files`
  * host `virtiofsd` / qemu FD counts
* The `geowatch` token subtree is currently the highest-value reproducer.
* Apparent “boot hangs” can actually be later-phase issues:

  * one case was really SSH host-key mismatch after the VM already had a DHCP lease
  * clearing known_hosts fixed it
* Restarting can clear transient bad states, but that does not identify root cause.

Implementation lessons:

* Generated helper scripts must preserve column-0 shebangs.
* Fail closed when manifest state is missing rather than replaying stale guest state.
* Heavy cloud-init replay is too blunt a mechanism for stopped-VM attach changes.
