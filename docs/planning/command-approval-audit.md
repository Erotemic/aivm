# Command approval audit

Generated inventory of every command submission affected by the
"a write is the guard" policy in `docs/source/design.rst`. Purpose is wholesale
review: confirm or correct the **Proposed** column, then the code change is
mechanical.

Rows marked **?** are ones I could not classify with confidence from the call
site alone and most want your eye.

## Dispositions

- **read** — inspects only. Declare `role='read'`. No prompt, and the command
  drops to `--verbose 2`. Many of these are undeclared today and default to
  `modify`, which is why they are in this table at all.
- **tool** — a write to aivm's own regenerable bookkeeping. Declare the
  ownership exemption. No prompt.
- **user** — a write to state the user owns, including the guest. Prompts.
  These need no marking; `user` is the default.

## Totals

| Disposition | Sites |
|---|---|
| read (misclassified today) | 33 |
| tool (exempt, must be declared) | 23 |
| user (prompts) | 88 |
| **total affected** | **144** |

Uncertain rows needing review: **35**

Of the 190 total command submissions in `aivm/`, 46
already declare `role='read'` and are unaffected.

## What changes in the code

1. `CommandSpec` gains an ownership field defaulting to `user`.
2. `_command_needs_approval` returns True for any `modify` whose ownership is
   not `tool`, replacing the `spec.sudo or _is_system_libvirt_mutation(spec)`
   test.
3. `_is_system_libvirt_mutation` is deleted; hypervisor control is subsumed.
4. `test_unprivileged_libvirt_mutation_keeps_approval_contract` encodes the
   overturned rule and is rewritten.
5. Each **read** row below declares `role='read'`; each **tool** row declares
   the exemption. **user** rows change nothing.


## Findings this audit surfaced

**Read probes are invalidating the probe cache.** 56 of 190 submissions declare
no role at all and inherit the `modify` default. `_execute_one` bumps
`mutation_generation` for every `modify`, and that counter is what probe caches
key on. So a plain `aivm status` run — 12 undeclared probes, none of which
change anything — invalidates the cache a dozen times. Declaring these `read` is
required by the approval policy anyway; the cache behaviour is a second reason.

**`aivm status --sudo` is not getting read-only auto-approval.** Same cause:
`auto_approve_readonly_sudo` only applies when the effective role is `read`, and
these probes are `modify` by default. Several are sudo probes, so today they
prompt (or consume approval) on a command that only reports.

**Grouping and classification are correlated.** Almost every undeclared site is
also ungrouped — the "not grouped into an explicit step" warning and this audit
are largely the same backlog seen from two directions. Wrapping a call site in
`mgr.step(...)` with `role='read'` fixes both at once.

**The exemption is smaller than expected.** Only ~23 of 144 affected sites look
like genuine aivm-owned bookkeeping. The policy's narrow bar holds up: most
writes really are to the user's host or the guest.

## Review method

Generated by AST-walking `aivm/**/*.py` for `.run(...)` / `.submit(...)` calls
on a command manager, recording the declared `role`, `sudo`, `check`, `summary`,
and any enclosing `mgr.intent(...)` / `mgr.step(...)` role. Dispositions are
proposed heuristically from the command text and the enclosing function name,
so they are a starting point for review, not a verdict — which is why uncertain
rows are marked.
